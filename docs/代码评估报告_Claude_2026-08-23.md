> **评估日期**：2026-08-23
> **评估对象**：`dev` 分支（HEAD `2042df9`，v5.0.0-beta.3），含工作区未提交改动
> **评估范围**：Go core（~5.8k 行）、Flutter 客户端（~3.4k 行）、CI/CD、构建脚本、依赖
> **方式**：只读静态审计，未修改任何源码，未执行构建（本机无 Go / Flutter 工具链）
> **说明**：本报告为独立复核，与 `docs/项目评估报告_2026-08-23.md` 结论部分重合，

## 执行摘要

架构方向是对的：Flutter 瘦客户端 + Go 厚核心 + gRPC 单一通道，边界清晰，业务逻辑单一真相源在
Go 侧。协议解析、配置构建两个最核心模块有真实测试（`link_test.go` 425 行、`build_test.go` 287 行），
这是这个仓库里质量最高的部分。

但**当前代码在端到端层面是不可运行的**：Flutter 从未拉起 `nekobox_core` 进程，也从未向 gRPC
传递鉴权 token，而 core 侧强制校验 token。这不是"某个功能有 bug"，而是主链路缺失。结合
UI 层多处必崩点（协议切换空断言）与安全缺陷（ZipSlip、路径穿越、更新包无签名），

**结论：不具备发布条件。当前状态更接近"架构骨架 + 单模块可用"，而非 beta。**

| 维度 | 评级 | 一句话 |
|------|------|--------|
| 架构设计 | B+ | 分层与职责划分正确，是本项目最大资产 |
| 端到端完整度 | **D** | 主链路（拉起 core + 鉴权）缺失，UI 设置项全为内存态空壳 |
| 代码质量 | C+ | Go 侧尚可；Flutter 侧存在空断言、错误吞噬、`dynamic` 滥用 |
| 安全性 | **D+** | 更新链路可任意写文件且无签名；gRPC 参数可控路径穿越 |
| 可靠性 | C | 错误遮蔽、nil 解引用、ID 碰撞、非原子写 |
| 测试 | **D** | Dart 侧唯一测试是 `1+1==2`；Go 侧仅 2 个模块有覆盖 |
| 工程化 | C | CI 用 `continue-on-error` / `|| true` 掩盖失败，可产出空壳包 |

## 一、阻断级问题（P0）

### B1. Flutter 从不启动 core，也从不传 token —— 主链路断裂 🔴

- `nekoray_flutter/lib/core/grpc/grpc_provider.dart:16-25`：`connectToCore()` 的 `token`
  默认 `''`。
- `nekoray_flutter/lib/core/grpc/grpc_client.dart:40`：`token.isEmpty ? {} : {...}` —— token
  为空时**不发送任何鉴权头**。
- `go/grpc_server/auth/auth.go:20-27`：core 侧无条件要求 `nekoray_auth` 头并做常量时间比对，
  缺头即 `Unauthenticated`。
- 全仓库 `grep -rn "Process\." nekoray_flutter/lib` **零命中**：没有任何代码启动
  `nekobox_core` 子进程，尽管 `libs/package_flutter_release.sh:64` 已把二进制打进发行包。
- `go/grpc_server/grpc.go:74-84`：core 在无 `--token` 时会**阻塞读 stdin** 索要 token。

**后果**：即使用户手动在终端起 core 并输入 token，Flutter 端也拿不到该 token，
所有 RPC 全部 401。`home_page.dart:46-48` 还把 `connectToCore` 的异常整个 `catch (_) {}` 吞掉，
UI 上看不到任何提示。

**修复方向**：Flutter 启动时生成随机 token → `Process.start(核心路径, ['nekobox','--token',t,'--port',p])`
→ 用同一 token 建连；进程生命周期与窗口绑定（core 侧的 `PR_SET_PDEATHSIG` 已就绪，
见 `parent_death_linux.go`，仅 Linux 有效）。

### B2. `Test` RPC 的 FullTest 分支：错误遮蔽 + nil 解引用 🔴

`go/cmd/nekobox_core/grpc_box.go:115-125`

```go
} else if in.Mode == gen.TestMode_FullTest {
    i, cancel, _, err := createInstance([]byte(in.Config.CoreConfig))  // := 遮蔽外层 err
```

两个缺陷：
1. `:=` 新建了局部 `err`，第 80-84 行的 `defer` 读的是**外层** `err`，永远为 nil ——
   创建实例失败时客户端收到一个空错误的成功响应。
2. `in.Config` 未判空。`UrlTest` 分支（第 89 行）做了 `if in.Config != nil`，FullTest 分支没有 ——
   一次不带 config 的 FullTest 请求即 **panic，整个 core 进程崩溃**。

### B3. 协议切换必崩 —— `DynamicForm` 缺 `didUpdateWidget` 🔴

`nekoray_flutter/lib/ui/components/dynamic_form.dart:72-83`：`_controllers` 是
`late final`，仅在 `initState` 中按当时的 `widget.fields` 填充。

`profile_edit_dialog.dart:285-294`：协议下拉 `onChanged` → `setState(() => _type = v)` →
`schema` 变了，但 `DynamicForm` 的 `key` 是固定的 `_formKey`，State **不会重建**。

于是 `_buildField()` 里 `controller: _controllers[f.key]`（新协议独有字段）为 null，
`collect()` 第 103 行 `_controllers[f.key]!.text` 直接**空断言抛异常**。

**在"新建节点"对话框里切一次协议就崩。** 这是最高频的用户操作路径之一。

### B4. 更新链路：ZipSlip + 无签名 + 无大小限制 🔴

| 位置 | 问题 |
|------|------|
| `go/cmd/updater/updater.go:42,53` | `extract.Zip/Gz` 解包到 `./nekoray_update`，**未校验条目路径**。恶意包内 `../../` 条目可写出目录任意位置。`github.com/codeclysm/extract v2.2.0+incompatible` 为 2017 年版本，已无维护。 |
| `go/grpc_server/update.go:116-128` | 下载产物写入 `"../nekoray-update.zip"`（相对 cwd，路径不确定），`io.Copy` 无 `MaxBytes` 限制，可写满磁盘。 |
| `go/grpc_server/update.go` 全文 | **无任何校验和 / 签名验证**。从 GitHub API 拿到 URL 就下、就解、就覆盖自身。 |
| `go/grpc_server/update.go:15` | `var update_download_url` 包级全局，Check/Download 两个 RPC 并发访问**无锁**。 |
| `go/cmd/updater/main.go:57-62` | `Copy()` 两个错误全部丢弃（`data, _ :=`），复制失败时静默继续；`ioutil` 已废弃；整文件读入内存。 |

对一个以 root/管理员权限运行、且自我覆盖的更新器而言，这套组合是提权路径。

### B5. rule_set 路径穿越（gRPC 参数可控）🔴

`go/grpc_server/core/ruleset/manager.go:94`

```go
path := filepath.Join(m.cacheDir, tag+ext)
```

`tag` 来自 `UpdateRuleSetReq.Tag`，**未做 `filepath.Base` 或白名单校验**。
`tag = "../../../../home/user/.bashrc"` 即可把远程内容写到任意位置。
另外 `NewManager("")` 默认 `cacheDir = "ruleset"` 是**相对路径**，缓存落点随 cwd 漂移。

### B6. `Exit` RPC 无条件终止进程

`go/grpc_server/grpc.go:30-34`：直接 `os.Exit(0)`。虽有 token 保护，但本机任意进程只要拿到
token（明文 gRPC over 127.0.0.1，token 通过命令行参数传递 → `ps` 可见）即可随时杀掉代理。
建议改为优雅关闭 + 命令行传 token 改为 stdin/环境变量/临时文件。

### B7. 依赖树严重漂移，CI 与 go.mod 声明冲突

| 模块 | go 指令 | 关键依赖 |
|------|---------|----------|
| `go/grpc_server` | **1.22** | `grpc v1.49.0`（2022-08）、`protobuf v1.28.1` |
| `go/cmd/nekobox_core` | **1.24.7** | `sing-box v1.13.19`（含新 grpc） |
| `go/cmd/updater` | **1.18**（EOL） | `extract v2.2.0`（2017） |
| `go/cmd/migrator` | 1.22 | — |

同一进程内 `grpc_server` 与 `nekobox_core` 会被 MVS 合并，实际生效的是高版本，
但 `go.mod` 声明的 `grpc v1.49.0` 意味着该模块单独 `go test` 时跑在 2022 年的 gRPC 上
（受 CVE-2023-44487 HTTP/2 Rapid Reset 影响）。

同时 `.github/workflows/{build-go-core,lint-test,release}.yml` 全部 `go-version: '1.22'`，
而 `nekobox_core/go.mod` 要求 `go 1.24.7` —— 目前靠 Go 的 toolchain 自动下载兜底，
构建可重现性和离线构建能力都被破坏。

## 二、高危问题（P1）

### 数据正确性

| ID | 位置 | 问题 |
|----|------|------|
| H1 | `providers.dart:64-66, 99-100` | 节点 ID = `millisecondsSinceEpoch.remainder(1e6) + pbBytes.length % 1000`。同毫秒内导入的多个节点若字节长度相同 → **ID 相同 → 后写覆盖前写，静默丢节点**。订阅导入一次几十个节点必然触发。 |
| H2 | `providers.dart:62-69, 97-106` | 批量导入是逐条 `saveProfile`，循环内抛异常直接 `return e.toString()`，**已写入的一半留在盘上**，且 group 记录未创建 → 孤儿数据。 |
| H3 | `profile_edit_dialog.dart:329-335` | `_buildEntity()` 重建 `StreamSettings` 时**只保留 5 个字段**（allowInsecure/publicKey/shortId/fingerprint/sni）。ws/gRPC/h2/httpupgrade 相关 20+ 字段、以及 `network`、`security` 本身，**编辑一次即全部丢失** → 节点损坏且不可用。 |
| H4 | `local_store.dart:50-55, 96-99` | `writeAsString` 非原子。写入过程中崩溃/断电留下截断 JSON，下次 `loadProfiles` 的 `catch (_) {}`（第 45 行）会**静默丢弃**该节点。应写 `.tmp` 再 `rename`（core 侧 `ruleset/manager.go:95-109` 反而做对了）。 |
| H5 | `local_store.dart` | 密码、UUID、Reality 私钥、SSH 凭据**明文存 JSON**，无平台钥匙串集成，文件权限用默认值。 |
| H6 | `routing_page.dart:435,441` | `rule.port.map(int.parse)` 无 try/catch。UI 允许输入 `80-443` 这类端口范围，一旦保存即抛 `FormatException`。 |

| ID | 位置 | 问题 |

| H7 | `grpc_box.go:68-72` | `Stop()` 清了 `instance` 和 `instanceCancel`，**没清 `instanceCtx`** → `QueryStats` 后续会拿着已取消的 ctx 做 `service.FromContext`。 |

## 三、中等问题（P2）

**订阅解析**
- `link.go:203-217` `decodeB64IfValid`：先补 `=` 再依次尝试 URL/Std 解码，会把恰好符合 base64
  字符集的**普通文本**误判为编码内容并返回乱码。应先校验字符集与长度合理性。
- `ParseSubscription`（`build_config.go:79-101`）把所有条目的错误拼成一个字符串，
  丢失了"哪一行失败"的定位信息。

**死代码 / 冗余**
- `core_box.go:140` `var _ = url.Parse // keep net/url import for future use` —— 应删除 import。
- `chain.go:87-89` `if cb, ok := bean.(*CustomBean); ok { _ = cb }` 空分支。
- `grpc.go:101-113` `RunCoreWithFlags` 无调用方，且硬编码 `os.Args[2:]` 与默认端口 19810，
  与 `main.go` 的 19821 不一致。
- `updater/updater.go:76-78` 仍在删 `nekoray.exe` / `nekoray_core.exe` 等 C++ 时代产物。
- `pubspec.yaml` 中 `tray_manager` / `window_manager` / `qr_flutter` / `collection` 四个依赖
  **零引用**（仅 `fl_chart` 被使用）。

**类型安全**
- `home_page.dart:255` `_showProfileActions(..., dynamic profile)` —— 明明可用 `ProxyEntity`。
- Go 侧配置构建大量使用 `map[string]interface{}`（`chain.go` / `outbound.go` 全篇），
  拼错 key 无编译期保护。sing-box 已提供 `option.Options` 强类型，建议逐步迁移。

**Go 模块治理**
- `go/.gitignore` 第 3 行 `*.json` —— 全目录忽略 JSON。目前 `git ls-files go | grep json`
  为 0，说明**测试 fixture 想加也加不进来**，且未来任何配置样例会被静默忽略。

## 七、值得肯定的部分

- **架构决策正确**：把配置构建、订阅解析、规则集管理全部下沉到 Go，Flutter 只做展示，
  避免了双份业务逻辑。这是相比原 C++/Qt 版本的实质性进步。

## 评估后新发现的阻断问题（比 B1 更根本）

**B0 · Dart 与 Go 的线格式不兼容** —— 出具报告后精读 `go/grpc_server/core/fmt/bean.go` 时发现：

- Go 的 `fmt.ProxyEntity` 要求 `{type,id,gid,latency,bean:{addr,port,stream:{net,sec,pbk,...}}}`
- 旧的 Dart `ProxyEntity.toJson()` 产出扁平结构 `{server,server_port,stream:{network,security,...}}`，**没有 `bean` 字段**
- 结果：`BuildConfig` 中 `DecodeBean()` 对 nil 反序列化，**每个节点都构建失败**
- 同样地 `Group.archive` 在 Go 是 `bool`、Dart 发 `int`，group_json 必定解析失败

已重写 Dart 数据模型对齐 Go 的 JSON tag，并保留 beta 版扁平格式的读取兼容路径。
